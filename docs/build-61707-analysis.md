### (1) Auth & authorization model — owner vs installer

**HTTP layer is unauthenticated (all four drafts agree).** `/etc/lighttpd.conf` loads `server.modules = mod_alias, mod_setenv, mod_cgi, mod_fastcgi, mod_openssl` — **no `mod_auth`, no `auth.require`, no `auth.backend`**. `/etc/lighttpd.d/` is empty, so the trailing `include_shell "find /etc/lighttpd.d ... -name '*.conf'"` pulls in nothing. The `mod_auth`/`auth_require` strings exist only compiled into `/usr/sbin/lighttpd` — never loaded. lighttpd also sets `Access-Control-Allow-Origin: *`. All authorization is pushed down into the CGI/FCGI processes.

**Two independent in-process authorization mechanisms — not one:**

- **(a) varserver `/vars` — real, enforced, Unix-uid ACLs.** `/auth` → `/usr/bin/fcgi_auth` (setuid root) issues `Set-Cookie: session=...; Secure; HttpOnly` via `libsessionmgr.so` → `/sessionmgr` socket → `/usr/bin/sessionmgr`. `/vars` → `/usr/bin/fcgi_vars` validates the cookie and `seteuid()`s to the session user's uid. Each varserver variable carries `"read"`/`"write"` role fields in its JSON definition (e.g. `/home/envoy_manager/config/varserver-envoy-manager.json` has `"read":"spwr_installer","write":"spwr_installer"`); `libvarserver` enforces via `geteuid`+`getpwuid`. An owner session is therefore denied installer-tagged vars purely by Unix uid.
- **(b) dl_cgi heavy endpoints (commission/*, grid/*, energy-storage-system/*) — NOT uid-gated in this build.** `/home/data_logger/bin/dl_cgi` does not import `seteuid/setuid/getpwnam/getpwuid/crypt/getspnam` and does not link `libsessionmgr`; it structurally cannot do uid/password authorization. Its only auth string is `"authorization header should not be used over an insecure connection"` — it inspects the Bearer header and **warns (does not block) on plain HTTP**. `grep -ic installer` on dl_cgi = 0: no installer/role/403 gating strings of its own. It delegates the actual work over D-Bus to SuperMan (`spwr.superman.dlcgi`), MIME, and ESMM.
- **(c) Python upload CGIs — static Bearer apikey, and disabled.** `/usr/lib/python2.7/site-packages/pvs/cgi.py` `authorize()` compares `Authorization: Bearer <key>` to `Platform()['apikey']` **only when `REQUEST_SCHEME == https`**, and in `endpoint()` the `authorize()` call is **commented out** (`# CM2 is not ready yet to use HTTPS`). The apikey is offline-derivable: `readplatform.sh apikey = sha256(/etc/api-key + serial chars 3-6,16-19)`, with the static salt `/etc/api-key = "‹redacted-salt›"`.

**The role model and how installer is issued.** Roles are three real Unix accounts (note the prefix here is **`spwr_`**, not the live-box `ssm_`): `spwr_installer` (uid 1000), `spwr_owner` (uid 1001), `spwr_guest` (uid 1002), plus `varserver` group. In `/etc/shadow` **all three role accounts are `!` (locked, no hash)** — only `root` carries a real `$6$` hash. Passwords are provisioned at runtime; no `chpasswd`/`usermod`/`crypt` script in the image sets them. `/etc/vars/sessionvars.json` holds `cfg_issuer="sunpower"`, `cfg_keystore="/etc/pubkeys"`, `cfg_timeout=300`, allowlist `cfg_users="spwr_installer,spwr_owner,spwr_guest"`. The installer tier is asserted via a **SunPower-cloud-issued JWT** (`SESSIONMGR_NewSessionFromToken` → `libtjwt` `TJWT_Validate`, RS256/RS384 via `PEM_read_bio_RSA_PUBKEY`) validated against the single 4096-bit RSA public key `/etc/pubkeys/9909687a-5c43-4ba7-bb72-237ef03bee32`. `jwttest` strings tie subject `installer`/`spwr_installer` to issuer `sunpower`/`sunpower.com`. The owner basic-auth password is serial-derived (last-5-of-serial, per prior analysis), validated against `/etc/shadow` via `crypt()`.

**Is the legitimate installer tier obtainable offline? No.** The `spwr_installer` shadow hash is `!` (nothing to crack); the elevated path is a JWT signed by SunPower's RSA private key (only the public key ships) and cannot be forged offline; there is no installer-password-derivation script (unlike the owner's serial-derived password and the static apikey).

**But the practical posture is far weaker than 61846, and the varserver ACL is bypassable with local root.** Because lighttpd enforces no auth and dl_cgi's commission/grid/ESS endpoints are not uid-gated, the dl_cgi REST API is effectively open at the HTTP layer on this build. Separately, anyone with **local root** (root has a real `$6$` hash, or via console/U-Boot `init=/bin/sh`) can `passwd spwr_installer` and then basic-auth as installer, satisfying the varserver `read/write:spwr_installer` ACLs — a local-root escalation, not a remote-API one. (Inferred) the installer gating the owner hits on 61846 was added after this build (consistent with < 61840), via later lighttpd.d config and/or fcgi_auth — it is not present in 61707's dl_cgi or lighttpd config.
